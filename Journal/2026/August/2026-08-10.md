Create `Test-Json.ps1`:

```
param(
    [Parameter(Mandatory)]
    [string]$Path
)

Write-Host "`nTesting: $Path" -ForegroundColor Cyan

try {
    $content = Get-Content $Path -Raw
    $null = $content | ConvertFrom-Json -ErrorAction Stop

    Write-Host "VALID JSON" -ForegroundColor Green
}
catch {
    Write-Host "INVALID JSON" -ForegroundColor Red
    Write-Host $_.Exception.Message -ForegroundColor Yellow
}
```

### Lesson Learned
1. What code belongs inside try? Anything you want to run once or try running.

2. Under what condition does catch execute? Any time the try is not in a successful output or any errors occur.

3. Why does this script use -ErrorAction Stop? The "ErrorAction" flag is used for error handling and the Stop value, is to stop the script or terminate the script run. The reason for this script to run this is, can not parse on a null value or at least that is my current read on this.

## 🔐 DevOps Micro-Quest — Seal the Main Branch

**Category:** DevOps / GitHub / Repository Security  
**Type:** Micro Quest
**Reward:** 25 XP  
**Status:** **Complete**

### Objective

Protect the Arcane Engineer Guild repository's `main` branch from unauthorized or accidental direct changes by implementing a GitHub repository ruleset.

### Work Completed

Configured a GitHub branch ruleset targeting the repository's **default branch (`main`)**.

The protection establishes a controlled contribution workflow:

```text
Working Branch / Fork
        ↓
      Commit
        ↓
       Push
        ↓
   Pull Request
        ↓
      Review
        ↓
       Merge
        ↓
       main
```

The purpose of the ruleset is to prevent contributors from directly pushing unwanted code into `main`. Changes must instead be submitted through the Pull Request workflow so they can be reviewed before becoming part of the Guild's canonical repository state.

### Configuration

- Targeted the repository's **default branch**
    
- Used **Include default branch** rather than hard-coding the `main` branch name
    
- Enabled Pull Request protection for changes entering `main`
    
- Established PR review as the controlled path for updating the default branch
    
- Prevented normal contributors from bypassing the intended review workflow
    
- Preserved the ability for contributors to work through branches or forks and submit Pull Requests
    

### What I Learned

I learned the distinction between:

- `origin` — the remote GitHub repository
    
- `main` — the repository's default branch
    
- Working branches — branches where development can occur without modifying the protected branch
    
- Pull Requests — the review gate used to introduce changes into `main`
    
- GitHub Rulesets — repository controls that enforce how protected branches may be modified
    

I also learned that targeting **Include default branch** makes the protection follow the repository's designated default branch rather than depending on a hard-coded branch name.

### DevOps Significance

This implements a real-world source-control protection commonly used in professional software engineering and DevOps environments.

Rather than trusting developers to remember not to push directly to the primary branch, the repository itself enforces the policy.

This follows the principle:

> **Enforce important safety boundaries through tooling rather than relying solely on human behavior.**

### Evidence for Guild Master Review

**Repository:** Arcane-Engineer-Guild  
**Protected branch:** `main`  
**Protection mechanism:** GitHub Ruleset  
**Required workflow:** Branch/Fork → Pull Request → Review → Merge → `main`

### Reflection

This change moves the Arcane Engineer Guild repository closer to a production-style development workflow. The `main` branch represents trusted Guild state, while development occurs outside that protected boundary.

Future repository automation, such as JSON validation and GitHub Actions checks, can be added to this Pull Request gate so invalid changes are automatically rejected before they reach `main`.
